Compiled at the start of Milestone 10 (post-launch stabilization).

## A note on evidence

**Project Forge has not yet been deployed to a real production environment** (Milestone 9 concluded
"READY WITH DOCUMENTED BLOCKERS" — no hosting provider, domain, or real Tech Impact Fellowship
applicants exist yet). There is therefore **no production error log, no support ticket queue, and no
real user feedback to draw from** — stating this explicitly per this milestone's own instruction not
to invent user feedback.

The evidence base for this register is instead:

1. A live, read-only data-integrity audit of the actual development database (queries and results
   below), which surfaces real state, not hypothetical state.
2. `docs/KNOWN_TECHNICAL_DEBT.md` — the accumulated, disclosed register of real issues found across
   every prior milestone's actual testing.
3. Direct code inspection of the hot paths this session's own live testing (Milestones 7–9) actually
   exercised — the mentor review queue, submission review, chat membership sync, application approval.
4. Regression re-testing of previously-verified security/isolation boundaries.

Any area with no real usage history (accessibility on a real device, actual production query latency
under real load, real notification-delivery patterns) is marked as such below, not guessed at.

### V11-001 — Chat channel roster missing historical members
- **Category:** Data Integrity
- **Affected role/workflow:** Student/Mentor — Fellowship Chat "who's in this channel" roster
- **Severity:** P2 (high-friction, not a security issue — access itself was never affected)
- **Evidence:** Live read-only audit this milestone: `student@test.local`, enrolled with
  `currentLearningTrackId` pointing at the "Software Engineering" track, was absent from that track's
  chat channel roster (`FellowshipChatChannelMember`).
- **Reproduction:** Any enrollment whose track channel was created *before* Milestone 8's
  `ChatMembershipSyncService.backfillTrackChannelRoster()` existed, and whose track selection also
  predates that fix, is missing from that channel's roster — the mechanism only fires on a *new*
  channel creation or a *new* track-selection event, never retroactively.
- **Current behavior → Desired behavior:** `GET /chat/channels/:id/members` omitted an actually-active
  participant → the roster reflects every currently-entitled student/mentor.
- **Proposed fix:** A one-time, idempotent reconciliation script
  (`prisma/repairs/repair-chat-membership.ts`) that re-runs the same entitlement logic
  `backfillTrackChannelRoster()` already uses, across every existing track channel, not just newly
  created ones.
- **Risk:** Low — purely additive (`upsert`), never deletes, never changes access authorization (which
  was already computed live and unaffected by this gap).
- **Status:** **Fixed and verified.** Script written, run against the live database (5 channels
  reconciled, 8 entitlement checks, 1 real gap closed), re-verified zero gaps remain via a second
  read-only audit. Unit test coverage added (`chat-membership-sync.service.spec.ts`, 7 new tests — this
  file previously had zero coverage despite being exactly where the gap lived).

### V11-002 — No notification when a mentor reviews a submission
- **Category:** Communication / Student Experience
- **Affected role/workflow:** Student — task submission review
- **Severity:** P2 (high-friction workflow problem)
- **Evidence:** Directly observed during Milestone 9's own live end-to-end verification: a mentor
  requested a revision on a real submission; the student had no in-app or email signal that this
  happened and would only discover it by manually re-opening the task. Confirmed by code inspection:
  `grep` across every module for a call into `NotificationsService` found exactly one call site
  (`AnnouncementsService`) before this milestone, plus `ChatMessagesService`'s reply notification — none
  for application status, task review, or mentor assignment. Confirmed by data: of 18 total
  `Notification` rows ever created in this database's history, 100% are `dm.message.received`.
- **Reproduction:** Approve or request revision on any `practical-task-submissions/:id/actions/...`
  action; no `Notification` row is created for the submitting student.
- **Current behavior → Desired behavior:** Silent status change → the student receives an in-app
  notification the moment a mentor approves or requests a revision on their submission.
- **Proposed fix:** `SubmissionReviewsService.recordDecision()` now calls
  `NotificationsService.notify()` after recording the decision, using the same fire-and-forget,
  never-blocks-the-transaction pattern `ChatMessagesService.notifyReply()` already established.
- **Risk:** Low — additive, non-blocking (wrapped in `.catch()`), reuses existing infrastructure
  verbatim, no schema change.
- **Status:** **Fixed and verified.** 3 new regression tests (approval notifies, revision-request
  notifies, a notification failure never fails the review decision itself).

### V11-003 — Mentor review-queue assembly has an N+1 query pattern
- **Category:** Performance
- **Affected role/workflow:** Mentor — review queue / dashboard
- **Severity:** P3 (no measured production slowness — Cohort 1's real scale is a capacity of 30
  students; this is a code-inspection finding, not an observed complaint)
- **Evidence:** Code inspection of `MentorDashboardService.listReviewQueue()`: submissions are fetched
  in one batched query, but enrollments, practical tasks, and review history are each looked up with
  one query *per distinct ID* via `Promise.all(ids.map(...))` rather than a single `findMany`/`in`
  query — three separate N+1 patterns in the same method.
- **Reproduction:** A review queue with N distinct pending submissions across M distinct
  students/tasks issues roughly `1 + M(enrollment) + M(user, already batched) + K(task) + N(reviews)`
  queries instead of 4 total.
- **Current behavior → Desired behavior:** Works correctly today; would degrade linearly as
  submission/student/task counts grow well beyond Cohort 1's near-term scale.
- **Proposed fix (not implemented):** Batch each lookup into a single `findMany({ where: { id: { in:
  [...] } } })`, mirroring the pattern `usersService.listByIds()` already uses in the same method.
- **Risk of the fix:** Low, but non-zero (touches a load-bearing mentor-facing read path) — not worth
  taking without a measured reason.
- **Status:** **Documented, not implemented** — per this milestone's explicit "avoid premature
  optimization" / "use evidence rather than assumptions" instruction. Revisit if a real cohort's review
  queue is ever observed to load slowly, or before scaling beyond a handful of concurrent cohorts.
